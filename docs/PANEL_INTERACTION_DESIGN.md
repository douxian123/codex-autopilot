# Codex 自动挡面板交互设计

> 根目录 `DESIGN.md` 是产品与视觉总契约；本文聚焦面板信息架构、交互路径和验收标准。

> 当前 `plugin/ui/panel.html` 是 **interim renderer / reference implementation only**，只用于验证数据契约和工程接线，不是最终视觉稿。最终面板正在重新设计；两者都必须消费 `docs/experience/panel-renderer-contract.json`，不得直接把当前 DOM、CSS 或卡片布局固化为最终规范。

## 产品判断

这个面板应该是 Codex 原生界面里的一层「挡风玻璃」，不是另一个任务工作台，也不应该是独立 Electron 应用。用户仍然在原来的 Codex 输入框里说话；面板只负责把系统状态压缩成几件值得人看的事，并在必须时接收人的确认。

首屏只回答三个问题：

1. **要不要我处理**：当前有没有需要用户确认、验收或拍板的事。
2. **是不是在干对的事**：系统现在在做什么、处于哪一步、有没有偏离预期。
3. **替我做成了什么**：最近真实闭环了什么、闭环率是多少。

一条原则是：用户不需要通过翻日志才能知道项目是否健康，也不需要为了看状态去理解七个管家各自在做什么。管家是内部实现，不是面向用户的导航结构。

## 闭环服务原则

面板不是施工进度看板，而是交付完成度和用户注意力的控制面。每个施工项在进入面板前都必须已经定义：用户从哪里使用、什么条件算真正生效、系统自己已验收了什么、还剩哪一个不可替代的人工判断，以及失败后如何恢复。面板不能把遗漏的入口、启动方式、验收步骤或收口动作留给用户自己发现。

面板上的“完成”只代表真实服务可用并且证据已闭环；代码提交、分支合并和机器测试通过只能作为证据条目，不能直接升级为完成。

## 形态与入口

- 承载：复用现有 MCP UI resource `ui://autopilot/panel-v2.html`，由 Codex 宿主渲染。
- 输入：用户原来的 Codex 输入框就是总输入框。面板输入框只保留在高级区作兼容兜底，默认不进首屏；两者共用路由逻辑。这样首屏不会同时出现两个「告诉我该做什么」的输入位置。
- 落点预览：高级区输入时实时显示「这句话将落到哪个项目」。判定清楚时直接显示项目名；无线索时显示「进全局待路由箱」，不猜进某个项目。
- 菜单栏 Companion 只做状态锚点：总开关、当前任务、需要人的卡点。它不承担完整项目管理。

不建议另起独立面板的原因：多一个窗口就多一次上下文切换，违背「减少用户盯盘」的目标。原生耦合也不意味着把宿主界面塞满；它只意味着入口无处不在、反馈集中在一屏。

## 信息架构

面板从上到下分成五层，前三层常驻，后两层按需展开。

| 层级 | 区块 | 回答什么 | 默认状态 |
|---|---|---|---|
| 0 | Codex 原生输入框与菜单栏快捷键 | 这句话会去哪 | 宿主常驻，不在面板里重复 |
| 1 | 要不要我处理 | 有什么需要人 | 有事才展开明细 |
| 2 | 是不是在干对的事 | 当前状态、当前工作、当前步骤 | 常驻，一段话加三个字段 |
| 3 | 替我做成了什么 | 闭环率、最近收口 | 常驻但只留摘要 |
| 4 | 管家健康条与工程详情与证据 | 七个管家、全局健康、工单、命令、截图、授权 | 健康条常驻但压缩；系统判据与证据折叠 |
| 5 | PM 简报与关系层 | 预期、验收标准、让路、跨项目目标 | 高级区折叠 |

首屏不应该出现的项目：进程 PID、守护绑定路径、管家逐行解释、原始命令全文、内部 ID、分支名列表、无差别日志流。它们不是没有价值，而是只应在用户主动排障时出现在工程详情里。七管家和全局健康必须保留可见状态，但应压缩成一条状态条，而不是八段说明。

## 第一屏的具体结构

### 1. 要不要我处理

用一条结论开头，而不是先放一个空卡片：

- 无需人参与：`不用你。系统正在自动推进。`
- 有验收：`有 2 项等你验收。`
- 有方向决策：`有 1 项需要你拍板。`
- 数据取不到：`取不到当前状态；不会把它当成正常。`

只有以下三类事项可以进入这一区：

1. 机器已经自验完、必须人看真实效果的人工验收；
2. 改产品方向、删数据、发布这三类决策；
3. 系统确实判不清归属或依赖，继续猜会造成破坏。

不要把“还有后台任务”“有一个 worker 在运行”“有若干条日志”当成需要用户关注的事项。用户只关心必须由自己做判断或确认的动作；其余由系统继续推进。

每项必须写清三件事：现在要你做什么、不做的后果、做完会怎样。人工验收项先由机器跑真实验证，截图只作为人眼复核附件；用户点「补图」不会替他收口。

### 2. 是不是在干对的事

这一区用一段人话状态加三个短字段：

- 现在是什么状态：运行中 / 已暂停 / 已关闭 / 取不到。
- 现在在干嘛：用业务语言描述当前工作项，不显示 worker ID。
- 现在在哪个步骤：规划 / 实现 / 验证 / 合流 / 验收；卡住时说明卡在哪。

状态点只使用四种语义：`attention`、`unknown`、`off`、`ok`。`ok` 不发光、不闪烁、不占额外篇幅；`attention` 才使用强调色并附带下一步动作。正常排队、可自动恢复的等待不算卡点。

系统状态行的首屏文案只说一句用户能据以行动的健康结论，例如「上下文健康：正常」。守护是否活着、上一轮时间、可落盘/冲突计数、逐条原因都进入「系统为什么这么判断」折叠区；`title` 保留同一串工程判据供悬停查看。队列读数取不到时写「取不到」，不能写 `0` 假装正常。

这一层还必须显示 PM 的产品判断结论：当前目标、当前阶段、方案是否仍有效；若执行证据与原始目标不一致，显示“路线需要重新规划”，并给出唯一下一步，不允许继续用“运行中”遮住偏离。

七管家和全局健康保留在首屏，但收进一条紧凑健康条：每项只显示名称和 `attention / unknown / off / ok` 状态，不显示解释性长句。全局健康是项目级结论，不是第八个施工管家。当前截图是八行展开态；目标态是一条健康条，明细进工程详情。落实时需要同步调整 `panel_logic_check.py` 里「一行一个角色」的断言，继续锁住八个键都存在、取不到不冒充正常，并补前后截图对比。

### 3. 替我做成了什么

只放两个东西：首问闭环率和最近三条真实收口。

- `首问闭环率 90.0%（9/10 已闭环）`
- 最近收口用「需求 -> 结果」的自然语言，例如：`视觉降噪：首屏三问已上线，门禁与真机渲染均通过。`
- 原始 `L-xxxx` 台账 ID 不进正文；保留在条目 `title` / `aria-label`，用户想追证据时可查，扫视时不被打断。
- 最近收口正文必须读成「需求 -> 结果」：不写 `kgctl`、路径、`progress.json`、`automation`、`越线`、`判不清归属` 等内部词；系统结论写人话，工程细节留在可访问属性和折叠证据里。
- 第一问摘要不只说「需关注」，要尽量说清下一步动作：`要你验收`、`要你拍板`、`要说一句`、`等自己的轮次`。项目文件夹里的工作项 ID、来源对话 ID 属于追溯证据，不进可见正文，只进 `title`。

取不到分母时写 `取不到`，不能写 `0%`。机器绿灯但没有真实证据的项不能算闭环。

最近收口优先展示“用户诉求 -> 可使用结果 -> 生效证据”，而不是“完成了某个任务”。如果结果尚未在真实入口可用，只能显示“已实现，待生效验证”，不能放入已完成列表。

## PM 简报：高级区的产品判断

PM 简报不是日志摘要，至少应包含：当前持久产品目标与用户价值；当前方案及采用原因；已查过的竞品/开源先验和 `adopt / adapt / build / defer / reject` 决策；当前施工路线、依赖和重复/冲突风险；最近一次结果复盘；以及当前仍然未知的事实和它对交付的影响。它默认折叠，用户需要判断路线时展开；不能把 PM 责任隐藏成内部台账，也不能把所有研究原文堆在首屏。

## 交互路径

1. **输入**：用户在 Codex 原生输入框或菜单栏快捷入口说一句话。
2. **预览**：高级区兼容输入框仍可显示落点项目和泳道；用户不需要选窗口、分支或角色。
3. **自动推进**：系统在隔离 worktree 中实现、验证、合流；首屏只更新当前状态和下一步。
4. **需要人时**：首屏出现明确动作按钮，说明点击后果和不点后果。
5. **收口后**：该项从「要不要我处理」消失，进入「替我做成了什么」；证据留在工程详情里可查。

6. **发现不完整或路线偏离**：面板不要求用户自己提出“这里是不是烂尾了”，而是由 PM 管家将项标为“未闭环 / 需要重新规划”，暂停后续新增施工，并展示重新规划的原因和影响。

约束候选第一次出现时只问一次：确认后进入机器门禁，拒绝后不生效。追问候选只提示建议话术，不自动向其他窗口发消息。

## 视觉取舍

- 底色保持浅灰白，卡片用白色和细边框；不使用深色大底、渐变或装饰性插画。
- 卡片圆角不超过 8px；状态用浅色小圆点或一个图标，不用彩色胶囊阵列。
- 层级顺序是：需要人 > 当前状态 > 最近结果 > 系统细节。前三项的正文不超过两行；超出部分进入展开区。
- 字号不做 viewport 缩放，长文本换行；窄窗口保持单列，不让文字盖住相邻内容。
- 计数、命令、路径、ID 一律进折叠区；首屏出现它们就是在消耗用户注意力。

### 原生感的技术落点（2026-11-19 调研）

这里的「原生感」不是复制 Codex 桌面包里的构建产物，而是遵守官方插件 UI 的设计系统，并用宿主包只校准密度和状态感。

唯一直接复用源定为 `@openai/apps-sdk-ui`。当前核对版本是 `0.2.2`，MIT 许可；它提供机器可读的 CSS token、Tailwind 4 集成和基于 Radix 的 React 组件，目标就是让插件 UI 贴近 ChatGPT/Codex 的原生容器。面板实现必须锁定 React 18 或 19，并按官方顺序引入样式：

```css
@import "tailwindcss";
@import "@openai/apps-sdk-ui/css";
@source "../node_modules/@openai/apps-sdk-ui";
```

样式分三层：`variables-primitive.css` 提供原始色阶和透明度，`variables-semantic.css` 提供语义变量，`variables-components.css` 提供组件局部变量。面板代码优先消费语义变量和组件变量，不硬编码六位色值；已有组件优先使用 `Button`、`Badge`、`Alert`、`Avatar`、`Input`、`Textarea`、`Select`、`Switch`、`Tooltip`、`Popover`、`Menu`、`Markdown`、`CodeBlock`、`Icon`，不再手写同类视觉原件。

`/Applications/ChatGPT.app/Contents/Resources/app.asar` 只作为只读校准样本。它是 Vite/React 构建后的 chunk，没有 source map、`.tsx` 或独立 design spec；`--d-stream-accent`、`--theme-accent-text`、`--input-font-size:16px`、`--select-control-font-size:14px`、`--alpha-08`、`light-dark(...)` 这类变量只能用来核对深浅色、密度、边框和状态感，不能整包复用，也不能据此声称拿到了原生组件源码。`~/.codex/App.main.tsx` 是 ThoughLoom 前端，旧版本 autopilot 的 `ui/panel.html` 是本插件面板，二者都不是 OpenAI 原生组件库。

协议层走 MCP Apps：工具通过 `_meta.ui.resourceUri` 关联 UI，iframe 内用 `ui/*` JSON-RPC 与宿主通信。数据读取和渲染拆成 data tool 与 render tool；面板只消费投影后的事实，不直接改配置、派活或替用户收口。官方 [Figma 组件库](https://www.figma.com/community/file/1625636989296445101) 只作版式参考，不替代代码里的 token 契约。

官方 UI 要求里与本项目最相关的约束：继承系统字体，不自定义字体；文本、图标、分割线使用系统色，品牌色只出现在 logo、badge 或主按钮；inline card 最多两个主操作；不做深层导航和嵌套滚动；carousel 保持 3 到 8 项；fullscreen 必须与宿主 composer 共存；PiP 只用于持续活动场景并随会话结束关闭。对 autopilot 来说，首屏阅读顺序仍是「结果标题 → 一个判断 → 最多两个动作 → 折叠的证据/状态」，内部计数、轮次、来源数量不进前台。

### Codex 原生线程拓扑与宿主能力边界（2026-11-19 落盘）

入口仍是用户原来的 Codex 输入框；`render_autopilot_panel` 注册 `_meta.ui.resourceUri = ui://autopilot/panel-v2.html`，并同时提供 `global` 与 `thread` 两个 entrypoint。面板不另造输入框，也不把自身伪装成独立应用。

派活到原生 Codex 时，目标拓扑是「🤖 Codex Autopilot 项目区 / section」下置顶「万法归一」总调度窗，子对话按统一格式显示在总调度窗下。当前 app-server 契约只有 `thread/start`、`thread/section/move`、`turn/start`，没有独立 `thread/rename`；Codex 侧栏标题又取自首条 user message，因此子对话首行就是标题契约：

```text
[AP][<project>][<lane>] <ledger_id> · <title>

<original body>
```

标题的项目、泳道、台账 ID 和简述都做短化与非法字符清理；原始任务正文必须完整保留。已有 `[AP]` 前缀时不重复添加；台账没有题名时固定显示 `自动挡任务`，不让正文首句冒充标题。派活自动归入按项目分桶的 section，同名 section 复用；section API 失败不拦派活，但要如实记录未归组。

这里的「永久置顶」和「侧栏默认展开」是宿主能力目标，不是插件能伪造的状态。当前工具面没有可用的 pin/default-expand API，所以不声称已实现；可落地且已落地的是 section 分组、官方 entrypoint 和首行标题命名。

主题 token 已按「官方 Apps SDK UI 语义 token → 旧宿主变量 → 独立浏览器兜底色」的顺序接入：底色、表面、文字、边框以及 success/warning/danger 的软背景与描边都优先消费 `var(--color-*)` 语义变量。机器门禁锁住这个顺序，避免后续把原生感退化成另写一套色板。改动前后的真实渲染截图分别是 `docs/panel-first-screen-before-native-contract.png` 与 `docs/panel-first-screen.png`；两者结构、颜色和间距一致，只有状态更新时间不同，说明本轮映射没有造成负向视觉变化。

## 相对当前截图的变化

当前截图已经有三问骨架，但首屏仍混入了太多工程内部读数：守护绑定错项目的大段路径提示、七个管家逐行状态、原始健康说明、长列表最近收口、工程详情里的命令与 ID。优化方向不是再加卡片，而是把首屏压缩成「一条结论 + 三个字段 + 一个闭环数字」，其余全部下沉。具体保留、下沉、删除如下：

| 内容 | 处理 |
|---|---|
| 需要人事项、当前状态、闭环率 | 保留在首屏 |
| 面板内输入框与落点预览 | 移到高级区，默认不可见 |
| 七管家与全局健康 | 收成一条紧凑状态条，明细进工程详情 |
| 项目文件夹、19 层工程进度、工作项表 | 进工程详情折叠区 |
| 命令、cwd、退出码、截图附件 | 进验收项详情，不进首屏正文 |
| 守护绑定路径、PID、队列读数、原始逻辑说明 | 进入「系统为什么这么判断」折叠区；异常结论仍在一屏可见 |
| 长最近收口列表 | 首屏最多三条，更多进历史 |

这不是删除可观测性，而是把可观测性从「默认展示」改成「需要时可查」。用户注意力是稀缺资源，面板必须先替他做过滤。

## 验收标准

1. 首屏任何状态下都能在 5 秒内回答三问；取不到数据时明确写 `取不到`。
2. 没有需要人的事项时，首屏不出现警告色、不显示长列表。
3. 每个「需要你介入」项都有动作、后果和完成后的去向。
4. 数据缺失、分母缺失、截图缺失都不伪装成 `0` 或 `正常`。
5. 现有 `panel_logic_check.py` 与 `panel_render_check.py` 必须继续通过；新增或调整首屏文案时同步更新门禁。
6. 改完前后各截一张真实渲染图对比，确认没有变丑、变乱或让文字溢出。

## 与底层架构的关系

面板不是管家本体，而是管家系统对外的一层薄界面。底层仍是「一入口、两平面、七管家、一层全局健康」：项目真相面决定什么值得给人看，执行面负责路由、实现、合并和状态；全局健康只读聚合事实。面板不得直接改配置、派活、改分支状态或替用户收口。
