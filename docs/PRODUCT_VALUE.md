# Codex 自动挡 · 为什么值得做完

> 本文是产品价值判断的固定文档，不是营销稿。价值是否成立要看「用户提一次需求
> 能否闭环」这条北极星，不看分支数、合并数、自检数这些动作指标。

## 一句话立足点

当前 coding agent 已经能写代码，但复杂项目真正难的不是写代码，而是需求分散、
对话和分支泛滥、共享工作区互相污染、合并反复打断人、做完了没有可复核的落盘。
Codex 自动挡不是再做一个调度界面，而是给 Codex 装一层本机控制面，把
「输入 → 归类 → 执行 → 验证 → 收口 → 回写」串成同一条链。

## 为什么这个位置值得做

1. 它解决的是 coding agent 最贵的那一环，不是写代码本身。
2. 官方原语已经能覆盖大部分能力，缺的是把 skill、MCP、worktree、gate、真相层
   连起来的控制面。
3. 复用公开扩展点，不 fork Codex、不另建多 agent 框架、不要求用户换 CLI。
4. 价值可以落在本机，不需要云服务、不需要网络权限，用户能关总闸回到原生状态。
5. 已有成熟工程实践佐证：worktree 隔离、收件箱分诊、spec 先行、串行 merge queue、
   issue/task 图当唯一事实来源，在开源项目里已经形成共识。

## 价值成立的判据

- 北极星：用户提一次需求就闭环的比例，分子分母可复现，算不出必须红。
- 用户只负责把模糊、零散、即时的感受丢进同一个输入框，不选对话、分支、角色。
- 真闭环必须走完：入口 → 归类 → 台账 → 独立 worktree → 真实验证门禁 → 落盘或
  诚实阻塞 → 真相回写 → 面板/菜单栏可见。
- 机器自证和人工验收分开：命令、cwd、退出码是机器证据；菜单栏可见、点开弹窗、
  真实手感、关总闸后的关闭态必须真人确认。

## 当前偏差

- 机器侧闭环已经基本打通，但真实桌面人工验收还没完成，不能把 A-0005/A-0006/
  A-0007/A-0008 当成已验证。
- 原生 dispatch 已能用真实桌面宿主创建 thread/turn/section，但完整闭环还缺
  “用户入口 → 面板/菜单栏可见 → 收口回写” 的真人演示证据。
- 面板首屏数据流已机器验证，观感和真实 Codex 面板的一致性还需要人眼确认。
- 如果只把动作数当成绩，就会把“机器自检通过”包装成产品价值成立；真正的价值
  来自一条真实需求从入口走到收口的闭环。

## 收口路径

1. 完成 A-0005：真人看到菜单栏图标、点开弹窗、确认总开关/当前任务/派活入口、
   `⌥⌘D` 回到 Codex 完整面板。
2. 完成 A-0006：在 Codex 面板看到真实状态，关总闸后看到明确关闭态。
3. 完成 A-0007：`⌥⌘S`、拖文件、服务菜单逐个真用一次，每次派完面板出现对应任务。
4. 完成 A-0008：用任意入口提一条真实小需求，观察自动归类、阶段变化、真实验证
   命令和收口结果，面板与菜单栏状态一致。
5. 人工验收通过后再更新验收台账和主线，不提前把 todo 标成 verified。

## 判定建议

值得做，且值得做到“机器闭环 + 真人桌面验收”都成立。它最大的风险不是做不出来，
而是把机器动作当成产品价值、把人工验收项提前关闭；守住北极星闭环率和真实证据
边界，产品价值才成立。
