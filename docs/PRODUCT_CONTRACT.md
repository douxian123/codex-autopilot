# Codex 自动挡产品契约

> 版本：2026-11-21
>
> 这份文档是产品定位、PM 管家职责、架构边界、执行标准和验收标准的统一契约。
> `docs/PRODUCT_MAINLINE.md` 是由真相层自动综合的当前状态视图，不替代本契约。

## 1. 产品定义

Codex 自动挡是一个**面向 Codex 项目开发的自主运行层**：用户只需要表达目标、问题或判断，系统负责持续理解、研究、规划、执行、验证、合并和回写；只有产品方向、删除数据、发布、语义冲突和必要的人工验收才打扰用户。

它不是新模型、第二个 IDE、通用 Super Agent、外部项目管理工具，也不要求用户安装或运行 Oh My Codex。Oh My Codex、DeepSeek Super-agent、Lauren Tan 的工程方法论及其他开源项目只作为先验研究来源；可复用的原则要内化为自动挡自己的模块和契约，不能把竞品作为运行时前置依赖。

研究结论的逐项 `adopt / adapt / build / defer / reject` 决策与落点由 `docs/research/adoption-strategy.json` 维护，并由 `python3 ops/test-research-adoption.py` 门禁验证。外部成熟实现优先吸收先验，不把竞品变成用户运行时依赖。

## 2. 用户结果

用户应当获得四个结果：

1. 任何入口都能把零散诉求送进一个项目级入口，不需要用户选择对话、分支或角色。
2. 用户说过的有效预期、决策和返修意见能成为可追溯约束，后续工作只取相关上下文，不把整本账喂给执行者。
3. 项目能围绕一个持久目标持续推进，自动完成可授权的工作，并在证据不足、路线不对或需要判断时停在明确的人工边界。
4. 用户只需关注项目是否在做对的事、已经完成了什么、还剩什么必须自己确认。

## 3. 最终架构

### 3.1 一个入口、两平面、四层运行契约

**一个入口**：Codex 原生输入框是主入口。截图、文件、菜单栏和其他入口都只负责把输入送入同一个 intake，不各自维护任务逻辑。

**真相面**回答“要做什么、为什么、什么算完成”：上下文、PM、验收、产品主线和用户约束。

**执行面**回答“怎么推进、怎么安全落盘”：路由、实现、合并、运行状态和资源边界。

**四层运行契约**：

| 层 | 必须负责的事 | 用户可见结果 |
|---|---|---|
| 关系层 | 持久目标、优先级、项目归属、人工介入时机 | 当前目标和需要用户关注的事项 |
| 规划层 | 需求理解、研究、方案、拆分、依赖、验收标准 | 为什么这样做、下一步是什么 |
| 执行层 | 隔离 worktree、实现、验证、合并、恢复 | 做成了什么、证据是什么 |
| 运行层 | 唤醒、调度、权限、预算、资源、审计 | 是否持续运行、为何暂停或等待 |

### 3.2 七类责任视图

“管家”是责任边界，不是七个常驻 Agent：

- 上下文管家：收录、去重、确认、分层召回用户预期。
- 路由管家：识别项目、工作项和泳道；不确定时进入待路由箱，禁止猜测落账。
- PM 管家：持续对产品目标、方案质量、施工路线和最终结果负责。
- 实现管家：按已批准方案和相关上下文在隔离环境中实现。
- 合并管家：防覆盖、防丢失、防破坏性修改，只有通过证据门禁才收口。
- 验收管家：机器先验收，再筛选最少的人工验收项，收集证据并闭环。
- 状态管家：监测运行健康和路线偏离，只提出受授权的正向调整建议。

全局健康是只读聚合层，不另造第八个管家，不直接改码、停任务或替用户决定。

上下文管家和 PM 管家共同承担 PRD 持续迭代职责：前者从全量反馈中提出可追溯的修订候选，后者基于研究、现场证据和当前上下文决定采用、适配、暂缓、拒绝或回问用户。PRD 是活契约，但不允许被零散反馈悄悄改写；不确定项必须显式进入用户决策，采用或适配必须先同步更新本文件并留下可复核证据。

## 4. PM 管家：产品质量责任人

PM 管家是整个产品开发循环的**持续质量责任人**，不是一次性的开工规划器。它要持续回答：

> 当前我们正在做的东西，是否仍然是基于用户真实意图、先验研究和现有证据所能得到的最佳方案、最佳设计和最佳实现路径？

### 4.1 PM 管家的六项职责

1. **意图确认**：提炼目标、用户价值、非目标、约束、授权级别和不确定项；隐含判断不得直接升级为全局硬约束。
2. **先验研究**：按风险和新颖度决定是否做竞品、开源、官方文档和既有工程研究；记录来源、许可证、维护信号、适用边界和事实置信度。
3. **方案决策**：比较 `adopt / adapt / build / defer / reject`，优先复用成熟能力；决定自研必须说明为什么现有方案不适用。
4. **施工规划**：把目标拆成有依赖、有边界、有文件占地、有验收标准的工程项，识别重复施工和潜在覆盖，规划最小风险路径。
5. **持续校准**：在实现、验证、合并和用户反馈后重新检查目标、范围、方案和验收标准；发现路线偏离时暂停新增施工，回到研究或规划阶段。
6. **质量负责**：对最终用户结果负责，而不是只对代码提交、门禁绿灯或任务数量负责。机器通过但产品目标未达成时，PM 必须保持未完成或重新打开。

7. **PRD 迭代负责**：每次用户反馈、实现结果、验收结论和路线变化后，重新检查本契约是否仍是当前全量上下文下的最优解；形成修订候选、做决策、同步 PRD，并在不确定时只问用户真正需要拍板的问题。

### 4.2 PM 闭环状态机

```text
intake
  -> clarify
  -> research_gate
  -> solution_decision
  -> delivery_map
  -> execute
  -> machine_acceptance
  -> human_acceptance (必要时)
  -> outcome_review
  -> close
                         ^
                         |
              route_drift / weak_evidence / new_constraint
                         |
                  replan / research_gate
```

每次进入 `execute` 前必须存在：目标、范围、方案决策、施工项、授权级别和验收标准。每次进入 `close` 前必须存在：真实验证证据、结果判断、未决风险和主线回写。

### 4.2.1 PRD 持续迭代闭环

```text
全量上下文/用户反馈 -> 修订候选 -> PM 决策
  -> adopt/adapt: 先更新 docs/PRODUCT_CONTRACT.md，再施工
  -> defer/reject: 记录理由，不改 PRD
  -> ask_user: 进入面板待决策，暂停受影响的施工
```

上下文管家只提出候选，不把反馈直接写成硬约束；PM 管家对产品质量和 PRD 当前性负责。执行闸必须能拦住“高影响修订未收敛仍继续开工”和“声称采用但 PRD 未更新”。

### 4.3 PM 的停止权和边界

PM 管家可以：

- 暂停新增施工；
- 要求重新研究或重新规划；
- 标记方案不再适用；
- 要求补充机器验收或人工验收；
- 将结果标记为 `unknown`、`needs_human` 或 `reopen`。

PM 管家不能未经授权：

- 改变用户产品方向；
- 删除数据或历史证据；
- 发布、推送外部生产环境；
- 覆盖他人工作区；
- 把不确定判断伪装成已确认需求。

## 5. 执行标准

### 5.0 闭环施工包：施工项不是半成品承诺

任何进入施工队列的工程项，都必须先形成一份“闭环施工包”。它不是任务标题，也不是待用户补充的草稿，而是该项能够交付并生效的完整定义：

- 服务结果：用户最终获得什么可使用的能力或结果，不能只写“改代码”或“补接口”。
- 使用入口：用户从哪里开始使用，首次使用需要什么最少动作。
- 生效条件：哪些代码、配置、账本、宿主加载、后台进程或发布动作必须真正完成。
- 机器验收：系统自己能运行的命令、cwd、退出码、产物和失败判据。
- 真实使用验收：必须在真实 Codex 宿主、真实项目、真实界面或真实数据上确认的部分。
- 人工边界：只有审美、手感、产品方向、删除、发布或无法自动判断的事项才进入用户队列，并说明为什么需要人。
- 回滚与恢复：失败、超时、冲突、资源不足和路线失效时如何保留和恢复。
- 最终回写：完成后更新产品状态、进展、验收证据、主线和判断逻辑。

缺少其中任何一项，工程项只能停在 `planning_incomplete`，不能进入 `execute`，也不能把补缺口的责任转嫁给用户。用户可以选择产品方向或验收结果，但不应该被迫替系统发现遗漏的使用入口、加载步骤、门禁或收口动作。

### 5.0.1 完成的定义

```text
目标确认 + 方案决策 + 闭环施工包完整 + 实现落盘
+ 机器验收通过 + 真实使用入口可达 + 必要人工验收完成
+ 失败/残余风险已记录 + 产品真相已回写 = closed
```

“代码完成”“测试通过”“已合并”都只是中间证据，不是产品完成。若真实入口不可用、面板无法发现、服务未启动或用户无法理解下一步，必须保持未完成或重新打开。

### 5.0.2 成本纪律：token-friendly，不以质量换省钱

```text
必留上下文 + 可判定验收 + 人工边界 = 不可裁剪
可选材料 -> 摘要优先 -> 命中缓存 -> 未命中才增量读取
预算触顶 -> block_and_report -> PM 重排范围，用户只看到必要决策
```

- 成本意识的生效前提是流程通畅、可用性、交付质量和现有体验无损；不得为了省 token 做负向工程、负向交互或把必做链路改成更难用、更慢、更不稳的版本。
- 成本约束只优化重复读取、重复计算和无关材料，不得删除目标、必留上下文、可判定验收、人工边界、回滚或真实入口证据。预算紧张只触发范围重排与报告，不触发降低交付标准。
- 上下文管家按 `scope + 文件指纹` 召回；文件、分支、main 头未变时直接复用缓存，并为缓存命中/失效留下可复核原因。
- 执行 prompt 默认摘要优先：先给条目、约束和验收结论，原始账本只在需要展开时增量读取；不可把整本上下文喂给执行者。
- 预算状态只有 `ok / blocked / unknown`。预算不足时停在开工前并报告缺口，不得静默截断上下文、跳过机器验收或伪造完成。
- 面板不展示 token 数值、轮次或内部计数；只有预算阻挡开工或需要用户决策时，才用一句人话说明原因和下一步。

### 5.1 任何任务开始前

- 必须先生成并校验闭环施工包；缺入口、缺生效条件或缺验收判据不得开工。
- 必须解析项目归属；不确定则进入全局待路由箱。
- 必须加载最小相关 Context Pack；不得无差别注入全量历史。
- 必须经过 PM 风险分级；需要研究的任务不能跳过研究门。
- 必须有目标、范围、非目标、授权级别和验收标准。
- 必须检查文件占地、重复施工和与在途工作的关系。
- 必须使用独立 worktree；不得直接污染用户正在使用的共享检出。

### 5.2 执行中

- 每个执行单元都必须有可追踪的工作项、分支、worktree、状态和心跳。
- 只允许在授权范围内读写资源；预算、磁盘、并发和重试都有上限。
- 退出 0 但无有效改动不能视为完成。
- 发现路线偏离、上下文冲突、重复施工或验收标准失效时，停止新增动作并回到 PM 复核。
- 后台持续运行的含义是“持续推进明确且已授权的项目目标”，不是无限派活或无限重试。

### 5.3 收口时

- 先跑机器验收，记录真实命令、cwd、退出码和产物。
- 合并前检查 ancestry、冲突、残留 marker、文件重叠和门禁。
- 合并失败保留现场，不删除未完成工作，不伪造关闭。
- 机器完成不等于产品完成；需要视觉、手感、真实流程或产品判断的项必须进入人工验收。
- 收口后同步问题、进展、产品状态、判断逻辑、验收和主线；结果复盘由 PM 管家重新判断。

### 5.4 PM 的持续服务质量循环

PM 管家每轮不是只问“任务做完了吗”，而要复核：用户能否找到入口并开始使用；系统是否按原始意图工作；用户是否知道当前状态、下一步和需要自己决定的事项；机器是否完成它能完成的验收；剩余人工事项是否已经最小化；结果、证据、风险和后续动作是否已回写。

任一答案为“否”或“取不到”，PM 管家必须选择修实现、补闭环施工包、重新研究、重新规划、等待用户或保持未完成，不能直接关闭。

## 6. 验收标准

验收状态以 2026-11-21 当前证据为准。勾选只表示该条已有当前机器门禁、真实入口渲染或端到端证据；用户小范围试用和持续使用频次没有现场证据时保持未勾选，写 `unknown`，不按 0 计，也不冒充完整愿景对外 Beta 已完成。

## 6.4 面板注意力契约

面板只需要让用户迅速知道三件事：现在需要我做什么、系统是否在做对的事、系统已经替我完成了什么。

用户必须关注：产品方向和范围变化、删除数据、发布、不可逆外部操作；机器完成后仍需人判断的视觉/手感/真实流程；项目归属不明、权限不足、外部依赖不可用、语义冲突或资源保护触发；以及结果是否已经在真实入口生效。

用户不应被迫关注：worker、lease、heartbeat、daemon tick、内部轮次、原始队列计数、分支列表、路径、内部 ID、原始命令全文、无差别日志和正常可恢复等待。这些进入“为什么这么判断 / 工程证据”折叠区。

面板顺序固定为：

```text
需要你做什么 → 当前是否按正确路线推进 → 已经替你完成什么
→ PM 简报 → 工程证据
```

每个动作都要说明“点了会怎样”和“不点会怎样”。如果路线偏离或施工项不完整，面板必须显示“未闭环 / 需要重新规划”，不能继续用“运行中”掩盖问题。

## 7. 参考实现的吸收原则

- 吸收 Oh My Codex 的需求澄清、持久目标、规划-执行-验证循环、阶段恢复和团队协作先验，但不要求用户安装它，也不把它作为运行时依赖。
- 吸收 DeepSeek Super-agent 的 Router/Worker、观察优先和持续主动原则，但把差异化放在项目真相、约束门禁、合并防丢失和验收证据。
- 吸收 worktree、spec-first、merge queue、append-only 事件账本等开源共识；能直接复用时优先复用，不能复用时记录 build 理由。
- 任何研究结论必须最终落到代码契约、状态机、门禁、面板字段或明确的“不做”边界，否则只算研究未落地。

## 8. 完成口径

产品只有同时满足以下四层才可以称为“对外 Beta”：

1. 工程链路门禁通过；
2. 真实 Codex 宿主加载、面板和入口现场通过；
3. 跨项目路由、持续运行、失败恢复和人工边界通过真实回归；
4. PM 质量验收和用户小范围试用通过。

只满足第一层，称为“工程实现完成”；只满足前两层，称为“内部 Beta 可用”；不得把它们表述成完整愿景已经击穿。
