# 司令台委派模板（发往其他 Codex 线程必须照此开头）

## 为什么有这个模板

2026-10-15 实测：阶段 1 监督线程用 `codex_app` 的 `send_message_to_thread` 发来一条
正文完整的委派（A-0085 重综合请求，含 commit、门禁命令、期望动作），接收窗口回了一句
「收到，当前日期按中国时区记为 2026 年 10 月 15 日」——委派内容一个字都没处理。

根因不是模型懒：同一轮 system/developer 注入里有一条
`<codex_apps_client_time_context>`（要求它用客户端时区回答面向用户的日期），
委派正文的 `<codex_delegation>` 块排在它之后。长上下文里，
一条「请求确认时间上下文」的指令优先级压过了后面那块项目内容，
于是它把整条委派归类成「时间确认」并照此作答。

**对策：让任务本身在开头 3 行内无可争议。**

## 模板（整段复制，只改尖括号里的内容）

```
【任务】<一句话：让接收方做什么动作，动词开头。例：把 ops/truth/mainline.json 里“网页 live 样本未跑”的表述改成“网页单样本已机器验证，完整 benchmark 阈值仍 unverified”>
【期望输出】<可核对的产出：改动的文件路径 + 要跑的验证命令 + 期望退出码；或“回一句话：改完/没改/卡在哪”>
【证据】<接收方需要的原始事实：commit sha、命令、cwd、退出码、文件路径。不要写“详见上文”>
【禁止】<越界范围。例：不动阶段 0 真相文件以外的任何文件；不改门禁阈值；不新建分支>
```

## 硬规则

1. **「【任务】」必须是正文第一行**，前面不要放时间、日期、环境、上下文说明。
2. 需要「在合适时机」这类模糊时机时，改写成明确条件（「本拍或下一拍」），
   否则接收方会把它当待办挂起来而没有任何动作。
3. 委派出去之后**不要在同一轮里再发第二条补充**（会再次落入同一误判）；
   要补充就发成包含【任务】头的完整重述。
4. 接收方是心跳线程时，它每拍有固定主打任务；把委派写成「可在本拍内完成的一步」，
   比写成需要多轮探索的大任务有效。
5. 发送后核对：下一拍读取接收线程 rollout 的最后一条 assistant 消息，
   确认它回应的是【任务】而不是别的块（时间/环境/确认）。
